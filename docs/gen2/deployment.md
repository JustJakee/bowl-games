## Current build contract

The checked-in [amplify.yml](../../amplify.yml) declares a monorepo application
with `appRoot: leaderboard`.

| Phase | Commands / artifact |
| --- | --- |
| Backend | `npm ci`, then `npx ampx pipeline-deploy --branch $AWS_BRANCH --app-id $AWS_APP_ID` |
| Frontend | `npm ci`, then `npm run build` |
| Publish | `dist/**/*` |
| Cache | `node_modules/**/*` |

`pipeline-deploy` is a real infrastructure deployment command. Local setup uses
`generate outputs` instead. No seed/reset command belongs in the hosting build.
Generated `amplify_outputs.json` connects the frontend to that branch's backend;
the prebuild hook copies outputs to public assets.

The original [Console setup document](../backend/amplify-gen2-console-deploy.md)
describes an earlier auth-only milestone. Its statements about no models,
CRA, no frontend wiring, and no build file are historical.

## Build failures addressed in Gen 2

- Backend resource imports now use explicit `.ts` suffixes, including
  `./auth/resource.ts` and `./data/resource.ts` in the backend entrypoint.
  Extensionless imports passed some local checks but failed the CI CDK loader.
- Root `tsconfig.amplify.json` uses NodeNext resolution, `noEmit`, and
  `allowImportingTsExtensions`.
- `amplify/tsconfig.json` extends the root configuration and maps `$amplify/*`
  to generated modules.
- Lambda environment imports use `$amplify/env/secure-picks` and
  `$amplify/env/registration-admin`. These modules are generated by Amplify,
  rather than manually committed environment files.
- The secure-picks function uses `getAmplifyDataClientConfig(env)` to configure
  its IAM-backed Data client before use.
- Amplify/CDK versions are pinned in the application package/lockfile to keep
  backend tooling behavior reproducible.
- Earlier schema fixes aligned field authorization and explicit `sub` identity
  claims to avoid generated owner/authorization conflicts.

## Local preflight

From a clean `gen2-updates` checkout, with required frontend outputs present:

```bash
cd leaderboard
npm run preflight:gen2
```

[preflight-gen2.mjs](../../leaderboard/scripts/preflight-gen2.mjs) checks the
branch and stops at the first failed step:

1. Lockfile installation.
2. Automated tests.
3. Root Amplify TypeScript check.
4. Backend-local TypeScript check.
5. Offline backend synthesis and Lambda bundling.
6. Frontend production build.
7. Staged and unstaged Git whitespace checks.

The offline synthesis probe uses installed Amplify internals and must be reviewed
when tooling versions change. It checks explicit local resource imports,
generates function environment artifacts for bundling, and refuses to overwrite
an existing `.amplify` or `tmp/gen2-offline-synth` directory. It does not deploy
AWS resources and cleans up its own generated artifacts.

## Live release evidence still required

Review complete staging build logs, actual Node/npm versions, generated change
sets and resource replacements, IAM scope, Lambda runtime behavior, AppSync
rules, Cognito email/group behavior, and frontend flows. A successful local
build or synthesis does not prove any of these live properties.

Schema changes can invalidate the seed tool's pinned introspection hash. Review
and rebaseline that hash against the approved staging backend before another
seed run; do not simply weaken target checks.

Use the full [predeployment runbook](../backend/gen2-predeployment-preflight.md)
and [registration staging checklist](../backend/gen2-registration-season-pending.md).
Record deployment results separately from implementation and local test results.
